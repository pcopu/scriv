# Actual-app Fountain export and reimport

This document describes source behavior and verification requirements. It does not publish historical execution records or attest to a passing run.

```sh
SCRIV_E2E_APP=/path/to/ScrivAutomation.app node tests/e2e/fountain-export.mjs
```

Requires the matching automation-enabled Catalyst app with `export-fountain`
and `import-fountain`. Native compilation and execution are pending. This is
an assertion map and boundary description, not a pass certificate.

## The production path exercised

`export-fountain` accepts no parameters beyond protocol `id` and `command`.
`ScrivCLIExport.exportFountain(workspace:)` validates its synthetic workspace,
arms one synchronous capture, then calls **`WorkspaceStore.exportScript()`**.
That unchanged production method:

1. Finishes editing through the normal application path.
2. Creates its UUID-named `ScrivExport-<UUID>` directory in app-owned temp.
3. Calls the existing production Fountain serializer and writes the resulting
   UTF-8 bytes atomically to `Script.fountain`.
4. Passes that exact file and its existing cleanup closure to
   `UIKitFileAccess.export(url:completion:)`.

Only at step 4, a `SCRIV_CLI_AUTOMATION`-guarded capture observes the generated
file instead of presenting the document picker. There is no direct serializer
call in the adapter, cloned serializer, in-memory fabricated export, project
assignment, alternative file writer or replacement cleanup implementation.
The capture invokes the **actual production completion** exactly once during
a successful operation. It remains armed while reading and cleaning up, then
is always cleared with `defer`. Failed observation does not fall through to a
picker. Missing or multiple handoffs/completions are errors, not successful
exports. Multiple handoffs are rejected and never observed as additional text.

The successful response contains only `dispatched`, `text`, `byteCount` and
`cleanupVerified`. Text is read from the actual generated file and limited to
65,536 UTF-8 bytes. The adapter checks that the generated directory no longer
exists after production cleanup, rather than treating invocation as proof of
deletion. The scenario reimports that exact text through the existing bounded
production import adapter, then observes app-owned persisted projects.

## Isolation and limitations

The helper and handoff capture exist only under `SCRIV_CLI_AUTOMATION`.
The helper requires `--scriv-cli`, `--screenshots`, a valid 36-character run
UUID and exact agreement with the app-computed fresh run root. The current
project must have a UUID and its package must be exactly this run's
`Projects/<id>.scriv`. Root, Projects and package directories are opened with
no-follow checks and verified as app-owned. The root must be private. Context
and descriptor identity are checked before export, at handoff and afterward.
A workspace must be mounted, without a presented modal or existing store
error. No error is cleared and no store/model state is assigned by the helper.

The output location is generated by the unchanged production exporter, not
supplied by the caller. It is outside the run folder but inside the same
app-owned temporary directory. The helper accepts only the exact callback URL
whose parent is `ScrivExport-<valid UUID>` immediately under that directory,
with basename `Script.fountain`. It does not scan temp directories, discover
old exports, accept arbitrary paths or request filesystem permissions. Only
the trusted system temporary prefix may resolve the macOS `/var` alias;
run/export-owned descendants may not resolve symlinks.

The export directory is opened with `O_DIRECTORY | O_NOFOLLOW`. Its file is
opened relative to that descriptor with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`;
it must be a regular app-owned file with one link and bounded size. The bytes
must match the observed file size and decode as UTF-8. File identity, size,
modification time and directory identity are checked around the read. Failures
return a generic adapter error, never underlying exceptions or local paths.
The output bound applies at capture: production may already have serialized
and written a larger synthetic project before the observer rejects it.

The production cleanup remains URL-based and removes its generated directory.
Descriptor checks do not lock that entire namespace against a separate process
that already has access to the same private app container. No such process,
external access grant or fallback is introduced here. If production fails
before reaching the handoff, its original failure/cleanup behavior is retained;
the adapter does not scan for or delete orphan directories.

This covers a **semantic application export with the real UTF-8 write and
cleanup**, plus actual import/validation/install. It does not cover picker
presentation, Cancel/Save UI, a chosen external destination, security-scoped
access, external copying, physical input, active-editor interruption or cold
reopening. No user file is read or shared. The scenario does not inject file
tampering, force an oversized export or simulate disk/cleanup failures; those
failure protections are source-reviewed, not runtime-certified by this slice.

## Additional scenario assertions

- Reject caller path, URL, filename, text and project ID fields without changing
  persisted projects.
- Each accepted export has the exact bounded response shape, matching UTF-8
  byte count and verified cleanup; it does not change persisted projects.
- Export twice independently from each source and require identical text.
  Repeated export after changing projects must capture the new source, not
  retained output from the previous capture.
- Each import adds one distinct saved project and preserves all prior projects.
- Observe the installed project title in the actual hittable workspace header,
  which also detects a picker accidentally covering the workspace.
- Finish with four saved projects: startup sample, its round trip, imported
  metadata source and metadata round trip, all unchanged from their observations.

source-state setup. Filename-fallback IDs `0010` and `0014` remain outside the
strict text-only import contract. No filename expansion, multiline Rename
